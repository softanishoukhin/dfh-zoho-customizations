# Release Notes — 2026-09-14

## ZP-TBD-65 — Pre-Need Scenario 1 (new pre-need, end to end)
Confirmed complete via live testing. Retainer invoice → Xero sync rebuilt from an
Invoice+Payment pair into a native Xero Receive Money transaction, coded to the Pre-Need
Liability account (26100) and posted against BNS DFH-Checking — `syncretainerinvoicetoxero`
(function id `5830143000019094452`), plus a matching rebuild of the ~7-minute catch-up Schedule
(`createRetainerInvoiceToXero`) and a trim of `syncretainerinvoicestatusbetweencrmandxero`
(function id `5830143000024812988`) to remove a now-obsolete Xero-status push. At-need side: a
new function, `addPreNeedDifferenceLineAndFlagRetainerCredit` (entity `retainer_invoice`),
detects a retainer applied to an invoice via a confirmed-live `invoices` array on the retainer's
own record, adds a single "Pre-Need Difference" line matched by product name (retainer line
items carry no `item_id` in this org, only `line_item_id`) for the price gap on contract items
only, then hands off to a small patch in the existing `createinvoiceonxero` (function id
`5830143000000527001`) which creates and allocates a real Xero Credit Note coded to Pre-Need
Liability, reusing that function's own Xero connection rather than opening a second one.

Two earlier Stage 2 designs were tried and superseded during build based on live test results,
not assumption — see `books/functions/preneed/ZP-TBD-65_preneed_scenario1_new_pre_need/metadata.md`
for the full narrative, including why each was replaced. Out of scope, confirmed with Andrea:
overpayment/refund case, cancellation process. Scenario 2 (historic migration, ~211 records) is
separate and not started.
